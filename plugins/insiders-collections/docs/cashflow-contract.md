# חוזה התזרים הצפוי: תוסף התשלומים ← דשבורד ההכנסות

תוסף התשלומים (insiders-collections) כבר מחובר לטרנזילה. הוא מושך את ספר הוראות הקבע ואת הסיכומים החודשיים של שני המסופים, ומגיש אותם לדשבורד ההכנסות דרך מסנן. הדשבורד לא צריך מפתחות של טרנזילה ולא צריך לפנות אליה בעצמו.

נבנה בגרסה 0.3.5 של תוסף התשלומים, מול insiders-finance-dashboard 0.63.5.

## איך קוראים

אותה צורה כמו `ifd_salary_summary`:

```php
$data = apply_filters( 'ifd_cashflow_forecast', null, array(
	'from'   => '2026-11', // YYYY-MM. ברירת מחדל: החודש הנוכחי
	'months' => 6,         // 1 עד 24. ברירת מחדל: 6
) );
```

- **`null`**: אין נתון אמיתי להגיש. תוסף התשלומים לא פעיל, או שהסנכרון מטרנזילה לא הצליח אף פעם. להציג את המקור כ-missing, לא כאפס.
- **מערך**: התשובה במבנה שבהמשך. גם כשהסנכרון האחרון נכשל, חוזר הערך האחרון הידוע, עם `stale` ועם השגיאה.

הקריאה לא פונה לטרנזילה. היא קוראת טבלאות מקומיות ומהירה, ואפשר לקרוא לה בכל טעינת מסך. הסנכרון מטרנזילה רץ בתוסף התשלומים פעם בשש שעות.

## מה כל סכום אומר

| שדה | מקור | מתי לסמוך עליו |
| :- | :- | :- |
| `scheduled` | הוראות קבע פעילות במסוף insiderstok. תאריך החיוב לפי `next_charge_date` של טרנזילה, ויום החיוב בחודש לפי `charge_dom`. הוראה עם מספר תשלומים מוגבל נעצרת אחרי התשלום האחרון | זה הבסיס של התזרים. המקור הוא מה שטרנזילה עצמה מתכננת לחייב |
| `at_risk` | אותן הוראות, כשיש סיבה לחשוב שהחיוב לא יעבור. `card_expired`: תוקף הכרטיס נגמר לפני חודש החיוב. `recent_failure`: החיוב האחרון נכשל ותוסף התשלומים עדיין גובה אותו. `overdue`: תאריך החיוב הבא כבר עבר ולא התקדם | לא לחבר ל-`scheduled` כאילו הוא ודאי. מומלץ להציג בנפרד, או לספור לפי שיעור הצלחה שהדשבורד מחשב |
| `collections` | מה שתוסף התשלומים צפוי לגבות בתאריך ידוע: חיוב מהכרטיס השמור שכבר תוזמן (`card_charge`), והבטחת תשלום שאושרה (`promise`) | הערכה. חיוב יכול להידחות ותלמיד יכול לא לעמוד בהבטחה |
| `open_unscheduled` | יתרות פתוחות שאושרו לגבייה ואין להן תאריך. סכום אחד, בלי חלוקה לחודשים | לא לפזר על חודשים כאילו התאריך ידוע |
| `actual` | דוח העסקאות של טרנזילה לכל מסוף: עסקאות שאושרו (קוד 000). `debit` הוא סכום עסקאות DEBIT ו-FORCE, `credit` הוא סכום הזיכויים (CREDIT), ו-`gross` הוא ההפרש. סוגים אחרים, כמו בדיקת כרטיס, לא נספרים ומופיעים ב-`other_types` | `complete: false` אומר שהחודש עוד רץ, או שעברו פחות מחמישה ימים מסופו (זיכויים מאוחרים). להציג כ-estimated עד שהוא נעשה true |
| `actual.*.failed` | חיובים שנדחו באותו חודש (קוד שאינו 000), בסכום שניסו לחייב. אף פעם לא נספרים כהכנסה | במסוף insiderstok כל דחייה היא חיוב של הוראה במחזור אחד, כי My Billing לא מנסה שוב (טרנזילה, 18.10.2026). לכן הסכום שתוכנן לחודש שעבר הוא `debit` ועוד `failed`. במסוף insiders דחייה היא ניסיון של קונה, שאולי שילם מיד אחר כך, ולכן היא לא הכנסה שהלכה לאיבוד |
| `unsupported_stos` | הוראות שאינן חודשיות או שאין להן תאריך חיוב | לא נכללות באף סכום. אם המספר גדול מ-0, צריך לציין שהתחזית חסרה |

## מסוף insiders (מיני חנות)

במסוף הזה אין הוראות קבע, ולכן אין לו עתיד בטרנזילה. יש לו רק היסטוריה: `history.insiders`, עד שישה חודשים מלאים אחורה ועוד החודש הנוכחי. תחזית למסוף הזה, למשל ממוצע או מגמה של החודשים האחרונים, היא חישוב של הדשבורד. תוסף התשלומים לא ממציא אותה.

## מיפוי למצבי IFD_DataPoint (המלצה)

| מצב בתשובה | DataPoint |
| :- | :- |
| התשובה היא `null` | `missing` |
| `sources.stos.stale` הוא true, או ש-`error` לא ריק | `syncfail`, עם הערך שהוחזר ועם `ok_at` כ-lastKnownAt |
| `scheduled` כשהמקור תקין | `measured` |
| `at_risk`, `collections` ו-`open_unscheduled` | `estimated`, עם הסיבה מ-`reasons` או מ-`kinds` |
| `actual` עם `complete: true` | `measured` |
| `actual` עם `complete: false`, או חודש עם `partial: true` | `estimated` |
| `unsupported_stos` גדול מ-0 | `suspect` על סך החודש |

## דברים שכבר טופלו בצד של תוסף התשלומים

אין צורך לטפל בהם שוב בדשבורד.

- דוח העסקאות מחזיר אגורות: 100 ₪ חוזרים כ-10000. בתשובה הסכומים כבר בשקלים.
- `stos/get` מחזיר את `charge_amount` בשקלים, למשל "247.2200". התשובה מאחדת את הסכומים.
- בתשובה החיה השדות נקראים `next_charge_date` ו-`last_charge_date`, ובתיעוד `*_date_time`. שתי הצורות נקראות.
- כשטרנזילה מחזירה רשימה ריקה לספר של יותר מעשר הוראות, התשובה נחשבת לתקלה ולא לביטול המוני: הספר לא מתעדכן ונרשמת שגיאה.
- הוראה שנעלמה מהרשימה הפעילה מסומנת כלא פעילה, ומפסיקה להיספר מהסנכרון הבא.
- הספר לא שומר שם, טלפון, מייל, תעודת זהות, טוקן או מספר כרטיס. נשמרים רק סכום, לוח זמנים, אחוז מע"מ ותוקף הכרטיס (חודש ושנה).

## דוגמה למקור בדשבורד

אותו חוזה של `IFD_Source`: הצלחה נשמרת ב-snapshot, כישלון נשמר ב-snapshot, והלג'ר לא נוגע. התחזית לא נכנסת ללג'ר, כי היא לא הכנסה שהתרחשה.

```php
class IFD_Source_Cashflow extends IFD_Source {
	public function key() {
		return 'icol_cashflow';
	}

	protected function fetch_and_store() {
		$data = apply_filters( 'ifd_cashflow_forecast', null, array( 'months' => 12 ) );
		if ( ! is_array( $data ) || 1 !== (int) ( $data['contract'] ?? 0 ) ) {
			throw new Exception( 'תוסף התשלומים לא מגיש תחזית (לא פעיל, או שעוד לא סונכרן)' );
		}
		if ( ! empty( $data['sources']['stos']['error'] ) ) {
			throw new Exception( 'סנכרון הוראות הקבע נכשל: ' . $data['sources']['stos']['error'] );
		}
		return $data; // נשמר ב-snapshot, והמסך קורא משם
	}
}
```

## לבדיקה באתר

בתוסף התשלומים, בכלי האבחון, הכלי `cashflow` מציג בדיוק את מה שהמסנן מחזיר. עם `&sync=1` הכלי מושך מטרנזילה מיד ולא מחכה לריצה הבאה.
